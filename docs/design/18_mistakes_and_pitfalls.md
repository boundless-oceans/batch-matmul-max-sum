# 本项目犯过的全部错误与问题（完整记录）

本文按**危害程度**排列，逐条给出：现象、根因、代价、修复、防止复发的检查项。
**目的：任何后续改动前先通读，避免重犯。**

---

## 一、导致平台掉分的错误（最严重）

### 1.1 `maxBuf` 容量不足 —— M > 4096 时越界

| 项 | 内容 |
| :--- | :--- |
| **现象** | 平台 `[ERROR][SetValue][65] index is 4096, which can not be larger than data len 4096` |
| **根因** | 行最大值缓冲只给 16KB（4096 个 float），而赛题允许 M ≤ 8192 |
| **误判** | 以为 `bmk_limit = 2^26` 会保护 —— 实际上 `B=4, K=256` 时它允许 M 到 65536 |
| **修复** | 扩到 32KB（8192 个 float），提交 `4223a48` |
| **教训** | **缓冲容量必须对着赛题"维度上限"逐条核算**，不能用间接约束推断 |

### 1.2 bf16 被当 fp16 处理 —— 平台 3 个测试点 Wrong Answer

| 项 | 内容 |
| :--- | :--- |
| **现象** | 平台首次提交：3 个 Wrong Answer，错误 100% |
| **根因** | `run_kernel` 硬编码 `elemBytes = 2`，忽略 `dtypeCode`；bf16 与 fp16 的位布局完全不同（1+8+7 vs 1+5+10） |
| **隐蔽处** | 还有一处更隐蔽的误分派：bf16 落入 `else` 分支，被构造成 `float*` 张量 |
| **为什么本地漏掉** | 本地测试集**没有 bf16 用例**，只有 fp16 |
| **修复** | 加 `Bf16ToFloat`（union 左移 16 位），并按"是否 16 位"统一分派 |
| **代价** | 0/15 → 7/15（修复后） |
| **教训** | **测试集必须覆盖赛题声明的所有 dtype**；判分用例 fp16 ×19、bf16 ×1 |

### 1.3 裸指针优化 —— 平台 Runtime Error，7/15 → 0/15

| 项 | 内容 |
| :--- | :--- |
| **现象** | 平台在点 1 直接 Runtime Error |
| **根因** | 为提速把 `GetValue()` 换成解引用 `GetPhyAddr()` 的裸指针 |
| **为什么本地抓不到** | **CPU 仿真下 GM 就是宿主内存，解引用必然成功**；真机 `__gm__` 空间不允许这样访问 |
| **修复** | 全部回退为 `GetValue()`（`dc901c6`） |
| **遗留判据** | 平台验证版里仍有一处 `GlobalTensor::GetPhyAddr()` 解引用（bf16 解码），且平台通过 → **该用法可行**；崩溃的嫌疑是 `LocalTensor::GetPhyAddr()` |
| **教训** | **不得依赖仿真特性获取性能**；`__gm__` 裸指针解引用是硬禁止 |

### 1.4 M 维并行版的竞态条件 —— 7/15 → 3/15

| 项 | 内容 |
| :--- | :--- |
| **现象** | 点 1-3 Pass、**点 4 错误 75%**、点 5-9 错误 100%、点 10 超时 |
| **根因** | workspace 放在 **x2 缓冲区内部**（`x2 + B*N*K*2 - 4096`），而主 kernel **在计算过程中**就写 `ws[u]` —— 覆盖了其它核仍在读的 x2 数据 |
| **为何 75%** | 竞态的表现：部分 batch 被踩坏、部分没被踩 |
| **为何点 1-3 全对** | 规模小，各核完成时间相近，来不及互相覆盖 |
| **修复** | 部分和先攒在 **UB**，**等所有 x2 读取结束后**再一次性写 workspace（`3a9cfd5`） |
| **教训 1** | **边算边写共享内存 = 竞态**；写共享区必须在所有读结束之后 |
| **教训 2** | 把 workspace 放进输入缓冲区内部是危险设计 |

#### 1.4.1 连带的判断错误：误以为"平台不支持跨核聚合"

我曾据仿真现象断定平台不支持跨核聚合，**这是错的**。
平台数据自证：点 1-3 全对、点 4 有一个 batch 正确 —— **若聚合不成立，这些应 100% 错误**。

**教训**：**不要用仿真行为反推平台行为**，尤其是多核内存语义。

### 1.5 未经验证就提交（流程性错误）

| 项 | 内容 |
| :--- | :--- |
| **事件** | 1.4 的版本在**明知"跨核聚合无法本地验证"**的情况下仍被推荐提交 |
| **代价** | 从 7/15 掉到 3/15 |
| **更深的问题** | 我当时把"题面要求 M 维并行"当作提交理由，但**题面要求 ≠ 我的实现正确** |
| **教训** | **本地无法完整验证正确性的改动，一律不提交。** 性能收益再大也不行 |

## 二、性能方向的失败尝试（12 类，均有实测数据）

| # | 尝试 | 结果 | 根因 |
| :-: | :--- | :--- | :--- |
| 1 | 向量化（tile 逐轮重建） | 7.7s → **300s+** | 逐元素 `SetValue` 做 tile 准备，标量开销是原版 8.1 倍 |
| 2 | 向量化（x1 载入 UB + `WholeReduceSum`） | 65ms → **60s+** | 同上 |
| 3 | 内层 4 路手工展开 | 3584 → **3883 ms** | 编译器本已优化，手工展开增加寄存器压力 |
| 4 | x1 整行 `DataCopy` 到 UB | **23791 ms（慢 25 倍）** | 逐行拷贝调用次数太多，摊不薄调用开销 |
| 5 | `LocalTensor::GetPhyAddr()` 裸指针 | 3584 → 3118 ms（快 13%） | **平台风险，不用**（见 1.3） |
| 6 | 关闭 `ASCENDC_DEBUG`（去边界检查） | 3742 ms | 断言开销可忽略 |
| 7 | `k` 外层 / `m` 内层（复用 x1） | **4737 ms** | 需引入 `dotBuf` 累加缓冲，净增访存 |
| 8 | 缓存友好化（交换循环顺序） | **8557 ms（慢 2.4 倍）** | 为使 m 连续需引入 dotBuf，把一次缓存未命中换成两次缓冲访问 |
| 9 | 上界剪枝（Cauchy-Schwarz） | **1.00x** | 标准正态数据下上界过松，剪不掉任何点积 |
| 10 | 编译优化 `-O2` | 无变化 | 瓶颈在仿真每次操作的固定开销，不在 x86 代码生成 |
| 11 | 双 kernel 方案（初版） | 平台 3/15 | 竞态（见 1.4） |
| 12 | 各类本地探针（`BMMS_LOCAL_PROBE` 等 7 种） | 全部失败 | 均破坏框架的 CPU 模式符号注入 |

### 2.1 失败模式总结

> **这些尝试都在"移动数据"。而本问题每个 MAC 必须读两个操作数
> （`2·M·N·K` 次读）——这个下界无法突破。**

**并且**：仿真的"向量运算"按元素逐个处理（约 5.5 ns/元素），与标量路径
（约 7.1 ns/MAC）同量级，故**仿真下向量化的最好情况只是与标量持平**。

## 三、测量与推断的错误

### 3.1 用进程总耗时当 kernel 耗时

| 项 | 内容 |
| :--- | :--- |
| **现象** | 早期所有性能数据都偏大，把参考计算（FP64）的时间也算进去了 |
| **修复** | 在驱动里分离计时，输出 `[timing] kernel = N ms ; 参考计算 = N ms`，并加 `skipRef` 参数 |
| **教训** | **测量前先确认口径**；把无关工作算进被测对象是最常见的性能测量错误 |

### 3.2 把"启动开销"误当"每次调用开销"

| 项 | 内容 |
| :--- | :--- |
| **现象** | 曾得出"仿真下每次向量调用固定 1 ms"的结论 |
| **真相** | 那是**进程启动开销**（约 240 ms）被摊到了少量调用上；实测每次 `Mul(1024)` 约 4.7 ms |
| **后果** | 基于错误模型得出的成本估算全部失真 |
| **教训** | **先测"零工作量"的基线**，把它减掉 |

### 3.3 用标量吞吐反推测试规模（量级错 4000 倍）

| 项 | 内容 |
| :--- | :--- |
| **现象** | 曾据"最优用时"反推总 MACs ≈ 61 万，得出"只需再快 10 倍" |
| **真相** | 最优实现用 **Cube（约 4096 MAC/周期）**，不是标量 1 MAC/周期 |
| **修正** | 真实测试规模比该估计大约 4000 倍 |
| **后果** | 优化方向与预期收益全部误判 |
| **教训** | **反推规模前必须先确认基线实现的硬件路径** |

### 3.4 超时单位读错（差 1000 倍）

| 项 | 内容 |
| :--- | :--- |
| **现象** | 一度把 `aclrtSynchronizeStreamWithTimeout(stream, 3000)` 的 3000 当作微秒 |
| **真相** | 单位是**毫秒**，即 3,000,000 µs |
| **后果** | 一度认为"超时很紧、可能被误报为 Runtime Error"，判断方向偏移 |
| **教训** | **API 的单位要查文档，不要靠印象** |

### 3.5 维度上限的枚举写错（低估 100 倍）

| 项 | 内容 |
| :--- | :--- |
| **现象** | 枚举最大规模时写 `min(8192, LIMIT//K)`，因 `LIMIT//K` 当 K 小时远大于 8192，`min` 恒取 8192，于是**每个 K 都算出 M=N=8192** |
| **后果** | 严重低估赛题允许的最大规模（真实可达 1.4e11 MACs） |
| **教训** | **枚举结果要抽查合理性**（不同 K 给出相同结果就是信号） |

### 3.6 关键容量结论（经实测校正）

| 项 | 值 |
| :--- | :--- |
| 每核 2.68e8 MACs | 约 3.9 秒 |
| **3 秒超时 ≈ 每核 2.1e8 MACs** | 这是容量上限 |
| 当前并行度 | `min(B, 核数)` |
| **B 小时的后果** | 每核 MACs = 总 MACs，**完全没有并行化** |

**这解释了"为什么前 7 个轻松、第 8 个过不去"**：测试点不按规模排序，
点 8 是"较大规模组"的第一个；一旦每核 MACs 越过 2.1e8 的台阶就超时。

## 四、对仿真能力的错误假设（本项目最大的时间浪费）

### 4.1 曾以为可以在仿真里测出向量/Cube 的收益

投入大量时间做向量化，最终确认：**仿真下测不出硬件加速收益**，
因为仿真按元素逐个处理，与标量同量级。

**正确认识**：仿真只能验**正确性**，**不能验性能**。

### 4.2 曾以为多核之间会聚合 GM 写入

反复设计依赖跨核共享的实现，最终发现仿真的多核行为**不确定**：

| 实测 | 结果 |
| :--- | :--- |
| 每核写 `y[0..3]` 为不同值 | 只有 core 0 保留 |
| 每核写 `coreId` 到 `ws[0..7]` | 全部 = 1 |
| 但 `B=3`（需要聚合）| **却能通过** |

**自相矛盾 → 不能用仿真推断平台的多核语义。**

### 4.3 曾以为 `ICPU_RUN_KF` 两次启动共享内存

| 实测 | 结果 |
| :--- | :--- |
| kernel1 写 999 到 x2 尾部，kernel2 读 | **读到 999** ✅ 共享 |
| kernel1 写 `y[0]=111`，kernel2 读 `y[0]` | **读到 0** ❌ 不共享 |

**又一次自相矛盾。** 结论同上：**不要用仿真推断平台。**

## 五、流程与工程错误

| # | 错误 | 教训 |
| :-: | :--- | :--- |
| 5.1 | 用全部 CPU 核编译导致电脑卡死 | **`nice -n 10 make -j8` 封顶** |
| 5.2 | 单次提交塞进写码+测试+修 bug | **多提交、小步走**，便于回退 |
| 5.3 | 合并分支后删除分支 | **不要删除分支**（保留可追溯性） |
| 5.4 | 测试锚点写死实现细节（launch 参数个数），实现一改就断 | 改用**合成注入式测试**，不锚定实现细节 |
| 5.5 | 断言写得比设计意图更紧 | 断言应表达**设计意图**，不是当前实现 |
| 5.6 | 用相近 API 搪塞不确定的 API | 不确定就**查文档或实测**，不要猜 |
| 5.7 | 注释里保留可推测个人电脑结构的路径 | 提交内容不得含个人信息与本地路径 |
| 5.8 | 照抄注释而非照抄可运行代码 | **以可运行代码为准** |
| 5.9 | 平台拒绝调试输出，而我此前记过却未落实到代码 | **规则要落成自动检查**（已有 `check_submit_compliance.py`） |

## 六、防止复发的检查清单

### 提交前必查

- [ ] `python3 tools/asc_stub/check_syntax.py`
- [ ] `python3 tools/check_device_calls.py`
- [ ] `python3 tools/check_submit_compliance.py`（含调试输出、本地探针残留）
- [ ] 本地回归**全部通过**（多 dtype、多转置、边界形状）
- [ ] **本次改动是否完全依赖本地可验证的性质？** 若否 → **不提交**
- [ ] 是否依赖 `__gm__` 裸指针解引用？→ **禁止**
- [ ] 是否在计算过程中写入会被其它核读取的区域？→ **禁止（竞态）**
- [ ] 缓冲容量是否对着**赛题维度上限**逐条核算？

### 性能结论必查

- [ ] 测量口径是否分离了参考计算与进程启动？
- [ ] 是否先测了"零工作量"基线？
- [ ] 反推规模时是否确认了基线实现的硬件路径？
- [ ] **这个结论是否依赖仿真特性？** 若是 → 不可用于平台决策

### 判断结论必查

- [ ] 是否在用仿真行为反推平台行为？→ **不可以**
- [ ] 观测数据是否自相矛盾？→ **矛盾即说明模型错误，不要择一采信**

## 七、最根本的一条

> **本项目最大的教训不是某一行代码写错，而是：**
> **把"仿真里跑通"当成了"平台上正确"，把"逻辑上应该对"当成了"验证过"。**

平台的正确性反馈（点 1-7 Pass / 点 8 超时 / 竞态导致 3/15）是**唯一权威判据**。
在拿到它之前，任何性能结论都只是假设。
