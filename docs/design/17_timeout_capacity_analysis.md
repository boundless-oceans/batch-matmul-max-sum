# 超时容量分析：为什么第 8 个点过不去

## 用户提出的关键问题

> 为什么光是第 8 个过不去呢，为什么前 7 个很轻松呢？

这是一个**结构性**问题。逐项分析如下。

## 一、测试点不是按规模排序的

从平台"最优用时"（µs）：

```
点1-7:   1.29 - 7.10      ← 小规模，全过
点8:     17.32            ← 断崖（点7的 4.7 倍）
点9-12:  50.68 - 85.25    ← 更大
点13-15: 5.21 - 6.95      ← 又变回小规模
```

**点 8 是"较大规模组"的第一个**。它超时后 9-15 全部 Skipped——
**所以真正过不去的是 8-12 这一整组，不只点 8。**

## 二、耗时由【每核 MACs】决定，而非总 MACs

**实测（kernel 净耗时，已与参考计算分离）**：

| 形状 | 每核 MACs | kernel 耗时 |
| :--- | --: | --: |
| B=1, M=N=1024, K=256 | 2.68e8 | **3884 ms** |
| B=4, M=N=1024, K=256 | 2.68e8 | **3967 ms** |

**两者耗时几乎相同**——因为每核 MACs 相同（B=1 用 1 核，B=4 用 4 核）。

**由此得到超时容量**：

```
每核 2.68e8 MACs ≈ 3.9 秒
=> 3 秒超时对应【每核约 2.1e8 MACs】
```

## 三、当前并行度下的容量

当前并行度 = `min(B, 核数)`，故：

```
每核 MACs = 总 MACs / min(B, 核数)
```

| 情形 | 每核 MACs | 结果 |
| :--- | --: | :--- |
| B=4, 总 MACs = 8.4e8 | 2.1e8 | 恰好卡在边界 |
| **B=1, 总 MACs = 2.1e9**（赛题允许的最大形状） | **2.1e9** | **约 39 秒 → 超时** |

**若测试点 8-12 用了较小 B（如 B=1）而规模较大，则每核 MACs 直接等于总
MACs——没有任何并行化，必然超时。**

## 四、这解释了断崖

``` 
点 1-7:  规模小 或 B 较大  -> 每核 MACs < 2.1e8 -> 轻松通过
点 8:    规模跨过台阶       -> 每核 MACs > 2.1e8 -> 超时
点 9-12: 规模更大           -> 必然超时（已 Skipped）
```

**不是"差一点"，而是并行度不足导致的容量台阶。**

## 五、M 维并行能提供多少容量

若按 `(batch, m 区间)` 切分到 `min(B*mSplits, 核数)` 个核：

| 核数 | 每核可承担 | 总容量 |
| --: | --: | --: |
| 4（当前，B=1 时只用 1 核） | 2.1e8 | 2.1e8 |
| **24（M 维切分）** | 2.1e8 | **5.0e9** |

**容量提升 24 倍**——足以覆盖赛题允许的最大形状（B=1, M=N=8192, K=32
共 2.1e9 MACs → 每核 8.9e7 → 约 1.3 秒 ✅）。

**这也呼应赛题 3.5 的明确要求：沿 B 维和/或 M 维合理分配多核任务。**

## 六、结论

| 问题 | 答复 |
| :--- | :--- |
| 为什么前 7 个轻松？ | 规模小，每核 MACs 远低于 2.1e8 的台阶 |
| 为什么点 8 过不去？ | 规模跨过台阶；且若 B 小则无并行度可用 |
| 差多少？ | 取决于 B：B 小则差**核数倍**（最多 24 倍），不是 1.5 倍 |
| 解法 | **沿 M 维切分**（赛题明确要求），但要解决跨核归约 |
