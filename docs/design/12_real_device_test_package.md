# 真机自测包（用于在 Ascend NPU 服务器上实测）

## 为什么需要真机

项目的核心困难是：**唯一能达标的两种手段，其性能收益本地都测不出。**

| 手段 | 本地可测性 | 原因 |
| :--- | :--- | :--- |
| 标量微优化 | ✅ 可测 | 但量级不够（与最优点差约 4000 倍） |
| **向量** | ❌ | 仿真把向量指令**逐元素模拟**，64 元素一次约 1.5 ms |
| **Cube** | ❌ | 高层 `Matmul` 挂住；底层 `Mmad` 需自拼且跨核不可验 |

此外，**平台的真实测试规模只能推测**（从最优用时反推，且最优实现的吞吐率
是猜的）。真机能直接给出答案。

## 包的位置

工作区根目录 `server_run/`（72 KB，可整体拷贝到服务器）。

## 包的内容

| 文件 | 说明 |
| :--- | :--- |
| `kernel.asc` | 待测实现 = 平台验证版（7/15）+ maxBuf 修复 |
| `main.asc` | 官方宿主驱动，**已加计时输出** |
| `CMakeLists.txt` | 官方构建脚本 + 可选的本地 CPU 仿真开关 |
| `bench.sh` | 分规模实测脚本 |
| `scripts/` | 官方数据生成与校验 |
| `README.md` | 用法与关键观察点 |

## 真机能回答的三个问题

### 1. 真实耗时距超时线多远

`main.asc` 已插入计时，输出：

```
[timing] run_kernel+sync = <微秒>  (availableCoreNum=<核数>)
```

**这个微秒数就是平台判超时的那个量**（`aclrtSynchronizeStreamWithTimeout`）。
`bench.sh` 分 16 个规模扫描，可定位超时线所在规模。

### 2. 平台实际给多少核

`availableCoreNum` 的值会打印出来。**本地一直是硬编码的 4，从未验证过真实值。**

- 若远大于 4，说明"按 (b, m 区间) 切分"有空间（当前并行度上限是 `min(B, cores)`）
- 这与"平台核数由 `ACL_DEV_ATTR_CUBE_CORE_NUM` 决定"的假设需要核对

### 3. 向量/Cube 的真实吞吐

把 `kernel.asc` 换成向量实现后重新编译，用同一套 `bench.sh` 测——
**这是本地做不到的对比**（本地向量版慢 900 倍，但那是仿真假象）。

## 已知的口径问题（本包已修正）

**本地"进程总耗时"不是 kernel 耗时。** driver 要做 O(B·M·N·K) 的 FP64
参考计算，实测在 4×1024×1024×256 上：

| 项 | 耗时 |
| :--- | --: |
| 进程总耗时 | 7540 ms |
| **真实 kernel** | **3892 ms** |
| 参考计算 | 3650 ms |

且**平凡核（只写常量）的真实 kernel 耗时恒为 70 ms**——纯固定开销。

本包的 `main.asc` 通过计时输出避免了这个口径问题。
