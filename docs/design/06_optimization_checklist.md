# 06 · 性能优化清单

本文件记录**按收益排序**的优化点。每条都标明依据、代价与前置条件。

评分规则（赛题六）：`100 / (1 + log_1.5(t/T))`，`t` 为本提交耗时、`T` 为最优性能；
**15 个测试点精度全过才计分**。`T` 基线的定义（赛题四.5）是
"`BatchMatMul + ReduceMax + ReduceSum` **拆分实现**的总耗时"——即三次独立
kernel 启动。故**融合本身就带来结构性加速**，这一点已由架构保证。

赛题四.5 还逐条点名了优化方向，本文件按它们组织。

---

## 1. 零成本项（写最终实现时立即做）

### 1.1 移除 `AscendC::printf`

`asc_printf.h:45` 的 `printf` 带 **`noinline`** 属性，位于 kernel 热路径。
探测版用它取回信息是对的，但生产版必须删除。

### 1.2 缓存 tiling，避免每次调用重算

`run_kernel` 每次被调用都会执行一遍 `MultiCoreMatmulTiling` 的
`SetAType`/`SetOrgShape`/`GetTiling`。同一测试点的 shape 与 dtype 不变，
**这份计算只依赖 (M, N, K, dtype, transA, transB, usedCores)**，可静态缓存。

**代价**：`run_kernel` 是同一个进程内被反复调用还是每用例一个新进程，尚未确认
（`OQ-023`）。后者的话缓存无效。**故这条要先确认再投入。**

---

## 2. 结构性优化：Cube 与 Vector 的流水（赛题四.5 第 1 条）

赛题明确要求"设计 BatchMatMul 和两级归约的协同流水"。当前设计是
**串行**的：AIC 全部算完 → 发 flag → AIV 全部归约。二者没有重叠。

### 2.1 用异步 `GetTensorC` 让归约与计算重叠

`GetTensorC` 的 `sync` 模板参数就是为此设计的（`matmul.h:293-299`）：

```cpp
template <bool sync = true>
void GetTensorC(const LocalTensor<DstT>& co2Local, uint8_t enAtomic = 0,
                bool enSequentialWrite = false);
```

`sync = false` 时取结果是异步的，**AIV 可以在 AIC 继续算下一块的同时归约上一块**。
这是本文件里收益最高的单点优化，且不改变数值结果（不涉及归约顺序）。

**前置**：需要 `OQ-020`/`OQ-021`（`__mix__` 与跨核 flag）先确认可用。

### 2.2 由此确认：C 的 format 必须是 NZ

`GetTensorC` 写 VECIN 的重载注释原文：

> `@param [out] co2Local: get C matrix to VECIN, data format only supports NZ`

**这直接回答了 `OQ-003`**：Cube 直写 UB 时 C 只能是 **NZ**，不是 ND。
登记册相应更新。

### 2.3 Double Buffer（赛题四.5 第 4 条）

两条独立的双缓冲，别混淆：

| 位置 | 开启方式 | 说明 |
| :--- | :--- | :--- |
| L1 / L0A / L0B / L0C | `tilingApi.SetDoubleBuffer(a, b, c, bias, ...)`（`matmul_tiling_base.h:497`） | 让 Matmul 内部的搬运与计算重叠 |
| 我们自己的 UB 队列 | `TQue<..., DEPTH>` 的 DEPTH > 1 | 当前探测版是 1（单缓冲） |

**代价与前置**：双缓冲占更多 L1/L0C。`SetBufferSpace(l1, l0C, ub, bt)`
（`:460`）可显式控制占用。**是否开得起取决于 baseM/baseN 的选择**，
需在阶段 7 用 `msprof` 的 buffer 占用数据判断，不宜凭猜测全开。

## 3. 归约本身的优化

### 3.1 跨 tile 累积最大值：省 88% 的归约调用

`large_square` 的输出 tile 数：

```
(B*M/baseM) * (N/baseN) = (4*1024/128) * (1024/128) = 32 * 8 = 256 个
```

**若每个 tile 之后都做一次 `ReduceMax`，就是 256 次向量归约。**
但沿 M 的求和只需在最后做一次，而每个 `baseM` 块内部各行的最大值才是需要
逐 tile 累积的量。改为**先把 tile 的 N 方向 max 累积进 UB 里一个
"每行当前最大值"缓冲**，全部 N 遍历完再做一次 `ReduceSum`：

| 方案 | 归约调用数 | 相对 |
| :--- | --: | :--- |
| 每 tile 一次完整归约 | 256 | 100% |
| 累积后一次归约 | **32** | **12%** |

**这不需要改变归约顺序**（仍是先 Max(N) 后 Sum(M)），故不触碰赛题四.3 的
硬性规则。

**实现注意**：每行的最大值必须对**该行的全部 N** 取，而每行的 N 在同一个
核内跨越 `ceil(N/baseN)` 个 tile。故累积缓冲的粒度是"本核负责的行"，
不是"本 tile 的行"。

### 3.2 多行打包成一次向量归约

`ReduceMax` 的 pattern 版接受 `srcShape[]`，可一次处理多行
（`Repeat` 是向量指令的天然批处理单位）。**逐行调用 128 次与打包成数次，
向量指令条数差一个量级**。这条与 3.1 相互增强。

## 4. 并行度：沿 B 维**和/或** M 维分配（赛题四.5 第 3 条）

这是当前设计与赛题要求**差距最大**的一处。

### 4.1 现状的代价

当前是 batch 对齐切分，活跃核数上限 = `min(B, 核数)`
（`05` §3 的实测表）。量化一下"若 M 维也切"能拿到多少：

| 用例 | B | M | 当前活跃核 | 若 M 维也切 | 提升 |
| :--- | --: | --: | --: | --: | --: |
| `large_square` | 4 | 1024 | 4 | 20 | **5.0x** |
| `m_large_n_small` | 2 | 2048 | 2 | 20 | **10.0x** |
| `b64_max` | 64 | 8 | 20 | 20 | 1x |
| `k8192_max` | 1 | 16 | 1 | 1 | 1x |
| `b_small` / `n_large_m_small` | 2–3 | 32 | 2–3 | 2–3 | 1x |

**收益集中在 M 大 B 小的用例**：`large_square` 与 `m_large_n_small`。

### 4.2 为什么当初没这么切

因为沿 M 切会让**同一 batch 的部分和落在多个核上**，需要跨核相加，
而本设计为规避原子加与预清零的风险选择了 batch 对齐（`05` 全文）。

### 4.3 现在可以怎么做（按风险排序）

**方案一：workspace 存部分和 + 二次归约（推荐先试）**

- 各核把 `(batch, core)` 的部分和写入 workspace 的一个槽位
- 再由一个轻量的第二 kernel（或同 kernel 内的一个核）把槽位相加得 `y[b]`

代价：多一次 kernel 启动（基线的三次启动相比仍是净赚）+ workspace 内存。
优点：**不需要原子加、不需要预清零**——避开了当初放弃 M 维切分的两条主因。

**方案二：原子加**

`SetAtomicAdd<float>` + `aclrtMemset` 清零 `y`，然后 `GetTensorC` 的
`enAtomic` 参数也能直接参与。代价是要处理 `SetAtomicAdd` 的"仅作用于下一次
搬运"这一易错语义，以及清零时机（`OQ-018`）。

**⚠️ 两种方案都有同一个隐患**：浮点加法的**非确定性**——不同核的写入顺序
不同，结果的最低位可能变化。而赛题四.1 明确要求
"**算子多次执行结果应保持一致**"。

**故这条优化的前置条件是**：先确认该"一致性"要求是**逐位一致**还是
**在容差内一致**（`OQ-024`）。若是逐位，方案一/二都不能用，
只能保留 batch 对齐——**当前设计就成了唯一正确选择**。

**这是本文件优先级最高、也最该先确认的一条。**

## 5. 搬运与复用（赛题四.5 第 2 条）

### 5.1 避免中间结果绕 GM

目标路径是 Cube 直写 UB（`04` §2.1），避免 `Matmul → GM → UB` 的往返。
已知限制：该路径的 C format 必须是 NZ（§2.2）。

### 5.2 L1/L0 复用

`SetDoubleBuffer` 与 `SetFixSplit` 配合 L1/L0C 的容量规划。属阶段 7 的
调参工作，需 `msprof` 数据支撑。

### 5.3 底噪位置：`large_square` 的启动开销占比

`large_square` 总 MAC 数 1.07e9，若 4 核各担 2.7e8，按 Cube 4096 MAC/cycle
估算约 16 µs。而 kernel 启动开销通常在 10–20 µs 量级。

**含义**：该用例可能**由启动开销主导**，此时把并行度从 4 提到 20
（§4.1 的 5x）对总耗时的影响**远小于 5x**。故 §4 的收益需实测确认，
不能只看并行度倍率。

## 6. 优先级建议

| 优先级 | 项 | 前置条件 | 预期收益 |
| :--- | :--- | :--- | :--- |
| **P0** | §1.1 移除 `printf` | 无 | 直接，热路径 |
| **P0** | §2.1 异步 `GetTensorC` 重叠 | `OQ-020/021` | 高，且不改数值 |
| **P1** | §3.1 跨 tile 累积 | 无 | 归约调用省 88% |
| **P1** | §2.3 选择性地开双缓冲 | `msprof` 数据 | 中 |
| **P2** | §4 M 维切分 | **`OQ-024` 的答案** | 5–10x 并行度，但有确定性风险 |
| **P2** | §1.2 缓存 tiling | `OQ-023` | 小（省一次 host 计算） |
| **P3** | §3.2 多行打包归约 | 无 | 中 |
| **P3** | §5.2 L1/L0 调参 | `msprof` 数据 | 未知 |

**总体判断**：P0/P1 都是**低风险且不改数值**的，应先做。P2 的 M 维切分
收益最大但风险也最大，**必须先解决 `OQ-024` 的确定性判据**；
在拿到 `msprof` 实测数据前不宜投入。

## 7. 本地仿真：本可绕开提交配额的手段（暂不可用）

CANN 9.0.0 支持两种本地运行模式，**若可用则能在不消耗提交配额的前提下验证
正确性**，价值高于本文件任何单点优化：

| 模式 | 开关 | 说明 |
| :--- | :--- | :--- |
| SIM 仿真 | `CMAKE_ASC_RUN_MODE=sim` | 链接 `$ASCEND_HOME_PATH/tools/simulator/<arch>/lib` |
| CPU Debug | `CMAKE_ASC_RUN_MODE=cpu` | 链接 `tikicpulib`，可用 GDB 断点调试 |

依据：`cmake/asc/asc_modules/CMakeASCInformation.cmake:88-129`，以及示例
`examples/01_simd_cpp_api/01_utilities/03_cpudebug/`。

**当前不可用**：两者都依赖 `ASCEND_HOME_PATH`（即已安装的 CANN 工具链），
本机没有 CANN、也没有 NPU。

**待确认 `OQ-025`**：本机能否安装 CANN 工具链以启用 CPU Debug 模式。
若能，则"改一次 → 本地跑一次"成为可行，验证成本从"一次提交配额"降到"一次
本地编译"，这会**根本改变本项目的迭代方式**——`tools/asc_stub/` 的语法检查
只能挡语法错误，而 CPU Debug 能验证数值正确性。

**注意**：平台评测用的是平台自己的 `CMakeLists.txt`，本地即使能跑也**不代表
评测环境一致**；CPU Debug 的结果只能作为正确性参考，不能替代平台提交。
