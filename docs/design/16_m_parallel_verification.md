### 途中修掉一个真实 bug

`rowMaxBuf` 的索引在 m-split 时混用了**全局 `m`** 与**局部 `i`**：
初始化与求和用 `i`，而 max 比较与写入用 `m`。`mBegin > 0` 时即读写错位。

## 未能验证的项（仿真限制）

### 现象：仿真下多核 GM 写入不聚合

| 实测 | 结果 |
| :--- | :--- |
| 每核写 `y[0..3]` 为 `coreId + 1000/2000/3000/4000` | `y[0]=1000`，`y[1..3]=0` |
| 每核写 `coreId` 到 `ws[0..7]` | **全部 = 1** |

**即只有部分核的写入保留。**

### 但存在矛盾

| 用例 | 结果 |
| :--- | :--- |
| `B=4, M=64`（每核一个 batch，需聚合 4 个核的结果）| ✅ **4/4 全对** |
| `B=8, M=64` | ⚠️ 7/8（最后一个 batch 错） |
| `B=16` | ⚠️ 15/16 |

**若多核写入真的不聚合，`B=4` 不可能全对。** 故仿真的多核内存语义
**无法用简单模型推断**——可能是"部分核共享、部分不共享"，或与执行顺序有关。

## 结论（已修正 —— 见文末"后续修正"）

**该方案的核心逻辑已逐项验证；唯一未验证的是"跨核聚合在平台上是否成立"。**

| 判断 | 依据 |
| :--- | :--- |
| 算法设计符合赛题要求 | 题面 3.5 明确要求"沿 B 维和/或 M 维分配多核任务" |
| 归约方式无需原子操作/跨核同步 | 用第二个 kernel，同一 stream 顺序执行 |
| 结果确定性 | 求和顺序固定为 `u = 0..workUnits-1` |
| **跨核聚合在平台上是否成立** | ⚠️ **未验证**（仿真测不出） |

**风险**：若平台也不聚合 → 结果错误。若平台正常（按 NPU 内存模型应当正常）
→ 并行度从 `min(B,核数)` 提升到 `min(B*mSplits,核数)`。

## 后续修正（重要）

**本文撰写时尚未发现竞态条件，故当时"风险：若平台也不聚合 -> 结果错误"的
判断是错的。平台实测（3/15：点 1-3 Pass、点 4 错误 75%、点 5-9 错误 100%）
揭示了真正的原因，并由此**证明跨核聚合是通的**：

| 证据 | 推理 |
| :--- | :--- |
| 点 1-3 **Pass** | 需要聚合才能得到正确结果 -> 聚合成立 |
| 点 4 **错误 75%** | 4 个 batch 中 1 个正确 -> 部分聚合成功 |

**若聚合不成立，这些应全部 100% 错误。**

### 真正的失败原因：竞态条件

workspace 放在 x2 缓冲区内部（`x2 + B*N*K*2 - 4096`），而主 kernel 在
**计算过程中**就写 `ws[u]`，覆盖了其它核仍在读的 x2 数据。

失败形态完全吻合：规模小的点（1-3）各核完成时间相近，来不及互踩；
规模大的点（5-9）时间差拉大，全部被踩；点 4 居中，部分被踩。

### 修复

部分和先攒在 **UB**，等**所有 x2 读取结束后**再一次性写 workspace。
**静态验证**：计算循环内 `ws[` 出现 0 次。

详见 `18_mistakes_and_pitfalls.md` 第 1.4 节。
