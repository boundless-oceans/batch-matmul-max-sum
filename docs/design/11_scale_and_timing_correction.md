# 关键更正：真实规模与真实 kernel 耗时

本文件更正此前若干错误结论。**这些错误导致数十轮优化投向了错误的目标。**

## 更正一：本地"进程总耗时"不是 kernel 耗时

driver 会在 CPU 上做 O(B·M·N·K) 的 **FP64 参考计算**，且每次乘法含两次
`half→double` 解码。故进程总耗时主要花在**验证**上。

**实测（分离计时后）**：

| 用例 | 进程总耗时（旧口径） | **真实 kernel** | 参考计算 |
| :--- | --: | --: | --: |
| 1×32×32×32 | 243 ms | **78 ms** | 1 ms |
| 1×512×512×32 | 441 ms | **198 ms** | 8 ms |
| 1×256×256×256 | 1650 ms | **313 ms** | 1200 ms |
| 4×1024×1024×256 | 7540 ms | **3892 ms** | 3650 ms |

**平凡核（只写常量）的真实 kernel 耗时恒为 70ms**——即固定开销（启动、
`GmAlloc`、仿真初始化），与规模无关。

故 4×1024×1024×256 的 kernel 时间中，**固定 70ms + 计算 3822ms**。

## 更正二：最优点用的是 Cube，不是标量

此前用 **1 MAC/cycle @1.8GHz**（标量假设）从"最优用时"反推规模，严重低估。
910B 单 Cube 核约 **4096 MAC/cycle**（16×16×16 每周期）。

按 Cube 吞吐重算：

| 点 | 最优用时 | 推算 MACs | 本实现预估（7.1 ns/MAC） |
| :-: | --: | --: | --: |
| 1 | 1.29 µs | 9.5e6 | 0.07 s |
| 8 | 17.32 µs | 1.28e8 | 0.91 s |
| 9 | 50.68 µs | 3.74e8 | 2.65 s |
| **12** | **85.25 µs** | **6.29e8** | **4.46 s ⏱️** |

**真实测试点规模是此前估计的约 4000 倍。**

## 更正三：超时确实由计算量造成

综合前两条：本实现在最大规模上需约 **4.5 秒**，而平台超时 **3 秒**。

**故超时是真实的性能不足，不是环境问题、不是挂起。**
此前"超时几乎不可能由计算量造成"的判断**错误**。

## 这解释了为什么标量优化是不够的

本实现是标量：每次乘加约 7.1 ns（CPU 仿真实测）。而最优点用 Cube，
吞吐高约 **4000 倍**。差距是**数量级**的，微优化无法弥补。

**结论：必须使用向量或 Cube 单元，标量路径没有出路。**

## 随之而来的困难

| 手段 | 本地能否验证性能 |
| :--- | :--- |
| 标量微优化 | ✅ 可验证（但量级不够） |
| 向量（`WholeReduceSum` 等） | ❌ 仿真把向量指令**逐元素模拟**（64 元素一次约 1.5 ms） |
| Cube（`Mmad`） | ❌ 高层 `Matmul` 挂住；底层需自拼数据流且跨核不可验 |

**即：唯一能达标的两种手段，其性能收益本地都测不出。**
这是本项目最根本的困难。

## 诊断版的价值（已作废）

曾计划提交"平凡核"以判断超时是否与计算无关。**基于上述更正，该诊断的前提
（"超时与计算无关"）已不成立，故无需提交。**

保留该分支（`diag/trivial-kernel`）作为记录，但不提交。
