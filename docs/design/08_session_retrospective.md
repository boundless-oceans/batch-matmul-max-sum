## 二、走过的弯路（按代价排序）

### 1. 把调试代码堆在一个未提交的工作区（代价最大）

**现象**：连续数十轮改动都不提交，一次方向错误就要全部重来。

**根因**：把"写代码、调试、测试、修 bug"当成一件事，想在一次提交里做完。

**已改**：本轮后半段拆成十余个提交，每个都是可回退的检查点，并用过
`git stash` 保护实验代码。

### 2. 在没有验证手段时就开始猜 API 语义

**现象**：向量化两次失败，都是因为对 `BlockReduceSum` 语义的推断是错的。

**根因**：搭不起探针环境，只能"改 kernel → 编译 → 看结果 → 再改"，
每个假设一轮，成本极高。

**正解**：**索引填充法**——令 `tile[i] = i`，则输出值直接告出参与了哪些
索引（28 → 0..7，496 → 0..31，2016 → 0..63）。**一次实验区分所有可能。**

### 3. 探针反复失败，却没有先查清框架的约束

**现象**：试了 7 种探针方案（独立文件、独立 `main`、独立 CMake 目标、
条件编译宏……），全部失败。

**根因**：CPU 模式符号（`GmAlloc`/`SetKernelMode`/`ICPU_RUN_KF`/启动桩）
**与 `main.asc` 这一个编译单元深度耦合**。任何"另起入口"的尝试都会破坏它；
新增 `__global__` 函数还会导致框架的 `AscCPUKernelLaunch` 生成失败。

**正解**：**临时改 `run_kernel` 的实现**——它是 `kernel.asc` 唯一的契约入口，
用它做探针不需要新入口。

### 4. 下负面结论太快

**现象**：判定"CPU 仿真不支持 Cube 计算"并写进文档，随后被反证推翻
（仿真库已实现 `Mmad`）。

**根因**：只看高层 `Matmul` 挂住就下结论，没查底层指令是否实现。

**教训**：**一条负面结论应当先找反证再下。**

### 5. 自己的调试残留造成误判

**现象**：driver 里留下一段"临时 tiling 生成"代码，向只有 4 字节的缓冲写
200 字节 tiling，导致内存破坏。此后多轮实验都被这个崩溃掩盖。

**教训**：**调试残留必须与实验同步清理**；崩溃出现时先查"我刚改了什么"。

## 三、证明有效的做法

| 做法 | 说明 |
| :--- | :--- |
| **本地 CPU 仿真** | 官方支持、规则允许，能验证正确性；但**与真机有结构性差异**（见下） |
| **数据驱动的判读** | 让 kernel 把中间值编码写回 `y[0]`（如 `100+id`、`nz*100+sum`），一个数字判定一个假设 |
| **索引填充法** | 一次实验区分归约 API 的所有可能语义 |
| **分步标记** | 逐步加代码、每步一个标记值，精确定位失败点（`Matmul` 的挂起点就是这样找到的） |
| **合规防线** | `printf`/`ASSERT`/探针残留等扫描器，把"记得删"变成"提交前硬报错" |

## 四、本地与真机的差异（重要）

| 维度 | 本地 CPU 仿真 | 服务器真实 NPU |
| :--- | :--- | :--- |
| 执行方式 | x86 模拟**单核** | Cube + Vector **真并行** |
| **`__cube__` 核里的向量指令** | 直接执行 | **报错**（Cube 核无向量单元） |
| 跨核同步 | 不工作（实测） | 工作 |
| 可用核数 | 24（本机） | **4**（平台 `availableCoreNum`） |

**推论**：

1. **Vector 路径**：本地与真机差异小 —— 本地方案可直接迁移，**优先选它**
2. **Cube 路径**：数值部分可验，**核间协同架构不可验**；而真机上 Cube 核
   不能执行向量指令，仿真会默默代跑（都是 x86），这是差异最大处

## 四点五、方法 1（向量化）的实测结果：两次尝试均失败

| 尝试 | 做法 | 结果 |
| :--- | :--- | :--- |
| 第一次 | 每个 (行,列,k块) 重建 tile | `large_square` 7.7s → **300s+**（+40 倍） |
| 第二次 | x1 载入 UB + `WholeReduceSum` | 中等用例 65ms → **60s+**（+900 倍） |

**失败原因**：准备向量数据的**标量操作数**远超标量版本：

| | 标量操作数 |
| :--- | --: |
| 标量版 | ~1.68e7 次 GM 读 |
| 向量化版 | **~2.1e9 次 `SetValue`/`GetValue`** |

**"把数据摆成向量单元要的形状"的成本，超过了直接标量计算。**
除非存在**免搬运**的 API（按步长直接参与计算），否则本问题的向量化不划算。

> 教训：**向量指令快，但把数据喂给它可能更贵。** 优化前应先估算
> "准备数据的成本"，而不是只看"计算指令的数量"。

## 四点六、规模反推：离达标约差 10 倍，而非 1000 倍

从平台各测试点"最优用时"反推（详见 [`09_optimization_plan_d1.md`](09_optimization_plan_d1.md)）：

```
平台超时 3,000,000 µs ÷ 点8最优 17.32 µs = 允许慢 17.3 万倍
我们实测约慢 1.5e5 倍  =>  离达标约差 10 倍
```

**该结论修正了先前"只有 Cube 能解决"的判断**（那个判断基于错误的倍数估计，
并导致在 Cube 验证上投入了大量成本）。

> ⚠️ 反推可靠性有限：最优用时在微秒量级，固定开销可能主导，未必正比于运算量。

## 五、下一步（方法 1：向量化 + `WholeReduceSum`）

### 为什么选它

| 依据 | 内容 |
| :--- | :--- |
| API 已打通 | `WholeReduceSum` 实测可一次归约整行 64 个元素 |
| 完全可本地验证 | 无 Cube 那种"本地能跑、真机报错"的风险 |
| 指令数大幅下降 | 标量 1.07e9 次乘加 → 预计 ~9.4e6 次向量指令 |

### 实现形状

```
对每个 (b, n, 行块)：
  装入 x1 的 rows 行 x 64 个 k 值     -> prod (rows, 64)
  装入 x2 第 n 列的 64 个 k 值并广播   -> work (rows, 64)
  Mul(work, prod, work)
  WholeReduceSum(work, work, 64, rows, 1, 1, 8)   <- 一次得到 rows 个行部分和
  累加部分和
```

### 已知约束

- `mask` 上限 64（fp32），故 K 按 64 分块
- `DataCopy` 自 GM 载入要求起始偏移 **32 字节对齐**；`K % 8 == 0` 时块偏移
  满足，否则需逐个取值
- 尾块必须补零（未清零的残留会被算进归约）
- 归约不应跨核，以保持结果确定性
