# 05 · 决策记录：行分配改为 batch 对齐

对应登记册的 **`OQ-006`**（原表述为"跨核相加 `y[b]` 如何完成"）。
本文件记录决策过程与依据，结论生效后 `OQ-006` 转为已解决。

---

## 1. 问题

原设计（`02` §1、`04` §4.1）把 `B*M` 行空间**均匀分给各核**，不保证一个 batch 的
行落在同一核上。后果是：**同一个 `y[b]` 会被多个核各写一部分**，而这些贡献必须
相加，于是需要跨核相加机制。

实测量化了触发范围：**12 个代表性用例中有 11 个**存在"一个 batch 被多个核覆盖"，
最多的一个 batch 被 17 个核覆盖。

## 2. 两个候选方案

### 方案 A：保留现状的均匀切分 + 跨核相加

各核算出自己那段行的部分和后，需要把多个贡献累加到同一个 `y[b]`。

- **必须用原子加**（`AscendC::SetAtomicAdd<float>()`，官方示例 `fill.asc:88` 有用法）
- 而原子加要求目标**预先清零**，否则会把上次运行的残留累加进来
- **待确认 `OQ-018`**：直调模式下在哪清零。候选是 `run_kernel` 内用
  `aclrtMemset`（host 侧 API），或在 device kernel 内先由一个核清零再同步。
  **本项仅在回到方案 A 时才需要解决**（§6 给出了将来可能回到方案 A 的条件），
  故保留登记而不随方案 A 一并取消
- 额外风险：`SetAtomicAdd` 的作用范围是"**下一次**搬运"而非持久生效，
  若在循环中反复设置/遗漏重置，会产生静默错误

### 方案 B：改为 batch 对齐切分

把每个 batch 的 `M` 行切成 `ceil(M / baseM)` 个任务，再把**任务**均分给各核。
由于同一 batch 的行始终连续落在同一个核上，**每个 `y[b]` 只被一个核写**，
跨核相加问题消失。

代价：当一个 batch 的 M-tile 数少于核数时，该 batch 用不满所有核。

## 3. 代价量化

### 3.1 并行度上限是 B，不是核数

**两条约束叠加**后，并行度上限由 batch 数决定：

- 约束一（不切 N）：`(b, m)` 行的完整 N 必须同核
- 约束二（`y[b]` 只被一个核写）：同一 batch 的全部 M 行必须同核

于是**一个核至少要负责一整个 batch**，活跃核数上限 = `min(B, 核数)`：

| 用例 | B | M | 20 核下活跃核 | 闲置 |
| :--- | --: | --: | --: | --: |
| `b1_min` / `tail_m` / `tail_n` / `k8192_max` | 1 | 1–32 | **1** | 19 |
| `m_large_n_small` / `negative_values` / `tail_mn` / `layout_ff` | 2 | 32–2048 | **2** | 18 |
| `b_small` | 3 | 32 | **3** | 17 |
| `large_square` | 4 | 1024 | **4** | 16 |
| `b64_max` | 64 | 8 | **20** | 0 |

> **这一节是修正。** 本节初稿只比较了"M-tile 数"，得出"代价几乎为零"的结论；
> 那个分析漏掉了约束二——它比"不跨 batch"更强：不是"行区间不跨 batch 边界"，
> 而是"同一 batch 的全部行必须在同一个核上"。加上约束二后并行度显著下降。

### 3.2 损失是否要紧：看 K 与总 MAC 数

并行度损失只有在 **Cube 计算占比高**时才影响耗时。实测各用例的规模：

| 用例 | B | K | 总 MAC 数 | 评价 |
| :--- | --: | --: | --: | :--- |
| `large_square` | 4 | 256 | **1.07e9** | **唯一的大用例**，4 核各担 2.7e8 |
| `n_large_m_small` | 2 | 64 | 8.4e6 | N 大但 MAC 少 |
| `m_large_n_small` | 2 | 64 | 8.4e6 | 同上 |
| `k8192_max` | 1 | 8192 | 2.1e6 | K 大但总量小 |
| 其余 | — | 32–64 | ≤ 5e5 | 微秒级 |

**结论**：并行度损失实质上只落在 `large_square` **一个**用例上（4 核 vs 20 核）。
其余用例要么总量极小（在微秒量级），要么 `B` 足够大。

而 `large_square` 恰好是 `B=4`、每 batch 规格完全相同，故 4 核之间**负载完全均衡**
（实测不均衡度 0.0000）。

## 4. 决策

**采用方案 B（batch 对齐切分）**，理由按权重排序：

1. **正确性上零风险**：每个 `y[b]` 只被一个核写，**结构上不可能写冲突**——
   不需要原子加、不需要预先清零、不受 `SetAtomicAdd` 作用范围易错的影响
2. **符合本项目的工作方式**：平台不能自助跑测试、每天上限 50 次提交，
   每次提交都可能消耗配额；把一整类并发正确性问题从设计里去掉，价值极高
3. **性能代价集中在单个用例**：只有 `large_square` 缺少并行度，且其 4 核负载均衡；
   该用例是否真的成为瓶颈，**须由阶段 7 的 `msprof` 实测判定，不预设结论**
4. 其余用例的活跃核数虽低，但总 MAC 数在 1e5–1e7 量级，属启动开销主导

### 4.1 留出的优化出口

若阶段 7 实测显示 `large_square` 因并行度不足而明显偏慢，优化方向是：

- 在 batch 内沿 M 或 N 切分并使用**原子加**累加 `y[b]`（`SetAtomicAdd<float>` +
  `aclrtMemset` 清零，官方示例 `fill.asc` 有完整用法）
- 代价是重新引入 `OQ-018`（清零在哪做）与原子作用范围的管理

**不预先实现**：该优化会显著增加出错面，而收益尚未证实。决策文档在此明确
记录它作为将来的出口，避免届时重新论证。

## 5. 实施影响

### 5.1 分配算法（已实现于 `simulator/tiling.py`）

分配粒度是**整个 batch**，而非单行或 baseM 块：

```
剩余 batch 数 = B，cursor = 0
for core_id in 0 .. num_cores-1:
    剩余核数 = num_cores - core_id
    剩余 batch = B - cursor
    if 剩余 batch <= 0:
        该核分空任务                      # batch 数少于核数
    else:
        take = min(ceil_div(剩余 batch, 剩余核数), 剩余 batch)
        row_start = cursor * M
        cursor += take
        row_end = cursor * M              # 恒为 M 的整数倍
```

**不变量**：每个核的 ``[row_start, row_end)`` 要么为空、要么完整覆盖若干个
连续 batch（两端都是 `M` 的整数倍）。这由 `rows_covered_once()` 的两条断言
守住：每行恰好被覆盖一次、每个 batch 恰好被一个核覆盖。

**待确认 `OQ-019`**：batch 数少于核数时，`blockNum` 应设为
`min(availableCoreNum, B)` 还是仍用 `availableCoreNum` 让空闲核自行跳过。
前者省启动开销，但要额外传参；后者简单。倾向后者（空闲核立即返回）。

### 5.2 与"按 tile 分配"的区别（一个已否决的方案）

初次实施时曾按 **`(batch, baseM 块)`** 的 tile 号连续分配。**该方案不满足
不变量**，实测两处反例：

- `B=2, M=17, baseM=8`：core 1 拿到 `[16,25)`，跨越 `b0` 与 `b1`
- `B=64, M=8, baseM=128`：每 batch 只有 1 个 tile，一个核拿到多个 tile
  就必然跨多个 batch

根因：tile 均分与 batch 边界不对齐，且"一个核拿多个 tile"在 `M < baseM` 时
等价于"拿多个 batch"。故**必须按 batch 而非 tile 分配**。

### 5.3 输出写回（`04` §6 相应简化）

既然每个 `y[b]` 只被一个核写，`04` §6 的 `OQ-005`（从 UB 向 GM 写单个 float）
变得简单：**每核把自己负责的每个 batch 的完整和直接写出**，不需要原子操作、
不需要预先清零。

## 6. 已知限制（随之而来）

**活跃核数上限为 `min(B, 核数)`。** 当一个 batch 的规模不足以填满一个核时，
并行度无法提升——因为把它的 M 行拆到多个核就必须跨核相加。

最坏情形是 `B=1`：无论 M 多大，都只有 1 个核工作。赛题可用用例中
`b1_min`、`tail_m`、`tail_n`、`k8192_max` 均属此列，但它们的总 MAC 数在
1e5–1e6 量级，属启动开销主导（§3.2）。

该限制登记于 `00_open_questions.md` §4 的"已知限制"。**若阶段 7 的 `msprof`
显示它成为瓶颈**，按 §4.1 的出口优化，而非提前实现。
