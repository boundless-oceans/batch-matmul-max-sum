# 提交前安全核查

针对"会不会超时或报错"这一问题的逐项核查记录。**区分"已确认"与"无法确认"**。

## 一、已确认：不会报错（本地验证覆盖）

### 1.1 正确性

| 维度 | 覆盖 | 结果 |
| :--- | :--- | :-: |
| **dtype** | fp32 / fp16 / bf16 | ✅ |
| **转置** | 四种组合（ff/tf/ft/tt） | ✅ |
| **形状** | 非 2 幂次、尾块、非方阵 | ✅ |
| **K 极值** | 32（下界）、8192（上界）、8 的倍数边界 | ✅ |
| **M/N 极值** | 1（下界）、8192（上界） | ✅ |
| **批量分配** | B 与核数整除/不整除（63/64/65/7/5/3） | ✅ |

**3 种 dtype × 16 个形状 = 48 项全部通过**，另加大 M/N 组合与批量压力测试。

### 1.2 数值解码（与 numpy 逐位比对）

| 解码 | 验证方式 | 结果 |
| :--- | :--- | :-: |
| **fp16 → fp32** | 7647 个位型与 numpy 逐位比对（含次正规数、inf、nan、符号位） | ✅ 全部一致 |
| **bf16 → fp32** | 已知位型 → 期望值（左移 16 位） | ✅ 6/6 |

### 1.3 缓冲区边界（已发现并修复一处真实缺陷）

| 缓冲 | 容量 | 对应上限 | 状态 |
| :--- | :--- | :--- | :-: |
| `colBuf` | 32KB = 8192 float | K 上限 8192 | ✅ 刚好 |
| **`maxBuf`** | ~~16KB = 4096 float~~ → **32KB** | M 上限 8192 | ⚠️ **曾有缺陷，已修** |

**该缺陷是真实可达的**：赛题 `bmk_limit = 2^26` **不构成保护**——

```
B=4, K=256  -> 它允许 M 到 65536（远超 m_max=8192）
```

故 M 取 5000~8192 合法且会被测到。原实现在 M > 4096 时报
`index is 4096, which can not be larger than data len 4096`。已修并回归。

### 1.4 溢出与终止性

| 项 | 结论 |
| :--- | :--- |
| 浮点溢出 | 标准正态输入，K=8192 时点积上界约 8192，M=8192 时总和上界约 6.7e7，远小于 float32 上限 3.4e38 ✅ |
| 唯一 `while` 循环 | fp16 次正规数规格化，最多 10 轮退出（已验证非死循环）✅ |
| 动态分配 | 无 `malloc`/`new` ✅ |
| 提交契约 | `run_kernel` 签名未变 ✅ |

## 二、无法确认：性能（平台超时）

**这是唯一剩下的风险，且我无法在本地消除。**

### 2.1 本地实测

| 用例 | 标量版起点 | 当前 |
| :--- | --: | --: |
| `large_square`（B=4,M=N=1024,K=256） | 7736 ms | **4236 ms**（1.83x） |

平台超时 3 秒。**本地 4.2 秒 > 3 秒**，但**本地 ≠ 平台**：

| 维度 | 本地 CPU 仿真 | 平台真实 NPU |
| :--- | :--- | :--- |
| 执行方式 | x86 模拟**单核** | 多核并行 |
| 核数 | 4（硬编码） | **未确认** |

### 2.2 为什么本地数字不能直接推断平台

- 仿真把**向量指令逐元素模拟**（实测每次 64 元素向量操作约 1.5 毫秒），
  故**向量化与 Cube 的收益本地完全测不出**
- 标量代码由 x86 原生执行，这部分**可参考**，但 x86 与 NPU 的标量路径
  性能比例未知

### 2.3 已知会超时的点

**平台测试点 8 在前两次提交中均超时**（且 9–15 因之被跳过）。
当前版本比那两次快 1.83 倍，但**是否足以过 8 无法确定**。

## 三、结论

| 问题 | 答复 |
| :--- | :--- |
| 会不会**报错**？ | **不会**（已本地验证，含边界与极值；并修复了一处真实越界缺陷） |
| 会不会**超时**？ | **无法保证**。本地比超时线慢约 1.4 倍；但本地测不出向量/Cube 收益，平台表现未知 |

**唯一能确定平台表现的方式是提交一次。**
