# 负面结果汇总（避免重复走死路）

本文件汇总**已尝试且失败**的优化方向，附实测数据与原因。
**目的：任何后续优化都先查这里，避免重复投入。**

## 平台现状

| 测试点 | 结果 |
| :--- | :--- |
| 1–7 | **Pass（错误 0.00%）** |
| **8** | **Time Limit Exceeded** |
| 9–15 | Skipped（因 8 失败而中断） |

**要过点 8 需约 1.5 倍提速。**

## 已失败的优化（全部有实测数据）

### 1. 向量化（两次，不同设计）

| 设计 | 结果 | 原因 |
| :--- | :--- | :--- |
| tile 逐轮重建 | `large_square` 7.7s → **300s+** | 标量准备开销是标量版的 8.1 倍 |
| x1 载入 UB + `WholeReduceSum` | 中等用例 65ms → **60s+** | 同上 |

**根本原因**：仿真下向量运算**按元素处理**（实测约 5.5 ns/元素），
与标量路径（约 7.1 ns）同量级；而向量化还要额外做布局/广播。

### 2. 内层 4 路手工展开

| 形状 | 基线 | 展开后 |
| :--- | --: | --: |
| 1×512×512×256 | 952 ms | **1029 ms**（更慢） |
| 1×1024×1024×256 | 3584 ms | **3883 ms**（更慢） |

**原因**：编译器本已优化；手工展开增加寄存器压力。

### 3. x1 整行 `DataCopy` 到 UB

| 形状 | 基线 | DataCopy 版 |
| :--- | --: | --: |
| 1×512×512×256 | 952 ms | **23791 ms**（慢 25 倍） |

**原因**：逐行拷贝的调用次数太多（M 次）。
**注**：`DataCopy` 本身在大块时很便宜（32768 元素每次约 0.21 µs），
但逐行拷贝无法摊薄调用开销。

### 4. `LocalTensor::GetPhyAddr()` 裸指针

| 形状 | 基线 | 裸指针版 |
| :--- | --: | --: |
| 1×1024×1024×256 | 3584 ms | **3118 ms（快 13%）** |

**不用**：`LocalTensor::GetPhyAddr()` 是上次平台 Runtime Error 的嫌疑来源
（`GlobalTensor::GetPhyAddr()` 已被平台验证可行——bf16 测试点通过）。
**13% 的收益不值得冒平台崩溃的风险。**

### 5. 关闭 `ASCENDC_DEBUG`（去边界检查）

| 形状 | 基线 | 关闭后 |
| :--- | --: | --: |
| 1×512×512×256 | 952 ms | 992 ms |
| 1×1024×1024×256 | 3584 ms | 3741 ms |

**原因**：`ASCENDC_DEBUG_ASSERT` 的开销可忽略。

### 6. `k` 外层 / `m` 内层（让 x1 值跨列复用）

| 形状 | 基线 | 新结构 |
| :--- | --: | --: |
| 1×512×512×256 | 952 ms | **1244 ms**（更慢） |
| 1×1024×1024×256 | 3584 ms | **4737 ms**（更慢） |

**原因**：需要额外的点积缓冲（`dotBuf` 的读写），净增访存。

### 7. 上界剪枝（Cauchy-Schwarz）

**实测加速比 1.00x**——标准正态数据下上界过松，无法剪掉任何点积。

### 8. 缓存友好化：交换循环顺序（k 外层 / m 内层，x1 连续）

**动机**：`transposeX1=false` 时，原实现按列读 x2 的步长为 `N` 个元素
（如 4096 字节），每次读命中不同缓存行；改为 k 外层后 x1 连续。

| 形状 | 基线 | 缓存友好版 |
| :--- | --: | --: |
| 1×512×512×256 | 952 ms | **2519 ms**（慢 2.6 倍） |
| 1×1024×1024×256 | 3584 ms | **8557 ms**（慢 2.4 倍） |

**原因**：为使 m 连续，需引入 `dotBuf`（每行一个点积累加器），
于是**每次 MAC 都要读写 dotBuf**——把一次缓存未命中换成了两次缓冲访问，
净亏。

**注**：x2 本身已在 UB 中（`colF`），故缓存未命中的影响远小于预期。

### 9. UB 读 vs GM 读的成本对比（测量失败）

多次尝试均被编译器优化掉（结果不依赖读取值）。已知的一次可用测量
（早先实验）显示二者**成本相近**（2031ms vs 2047ms）。

## 模式总结：为什么这些优化都失败

| 尝试 | 本质 | 结果 |
| :--- | :--- | :--- |
| 1,2 向量化 | 用向量指令替代标量 | 仿真下两者每元素成本相近，且需额外布局开销 |
| 3 DataCopy | 用批量搬运替代逐元素读 | 调用次数多，摊不薄 |
| 4 裸指针 | 去掉 `GetValue` 的边界检查 | **唯一有效（13%）但有平台风险** |
| 5 关闭断言 | 去掉边界检查 | 开销可忽略 |
| 6,8 换循环顺序 | 改善缓存局部性 | 需引入累加缓冲，净亏 |
| 7 剪枝 | 减少计算量 | 上界过松，1.00x |

**共同点：这些尝试都在"移动数据"，而本问题每个 MAC 必须读两个操作数
（`2·M·N·K` 次读），这个下界无法突破。**

### 10. 双 kernel 方案（提高并行度）—— 本地无法验证

**动机**：当前并行度上限是 `min(B, 核数)`。若某测试点 B=1 而平台给 24 核，
则 23 个核空闲。改为按 `(batch, m 区间)` 扁平切分可把上限提到核数。

**设计**（不需原子操作、不需跨核同步）：
```
run_kernel():
  kernel1<<<cores>>>: 每核负责一段 (b, m区间)，把"行最大值之和"写入 workspace
  kernel2<<<1>>>:     把 workspace 的部分和累加成 y[b]
```
两个 kernel 在同一 stream 上顺序执行；求和顺序固定，故结果确定。

**实测结果：本地无法验证，方案未完成。**

| 现象 | 数据 |
| :--- | :--- |
| `finalize` 是否执行 | ✅ 执行（写入 -777 可见） |
| 主 kernel 是否执行 | ✅ 执行到"进入工作单元" |
| **跨 kernel 的数据可见性** | ❌ **主 kernel 写 `y[0]=111`，finalize 读到 0** |

**根因**：`ICPU_RUN_KF` 每次调用会重新 `GmAlloc` 系统 workspace 并重置仿真状态；
实测**两次启动的内存不共享**。

**关键判断**：生产路径（`<<<>>>` kernel launch）在同一 stream 上应当共享内存，
故该设计**可能**在平台可行——但**本地完全无法验证**，而调试正确性又缺少手段。
**故放弃**：不提交未经正确性验证的实现。

### 10b. 双 kernel 方案的真正失败原因：**竞态条件**（已确诊）

平台实测：**从 7/15 掉到 3/15**（点 1-3 Pass、点 4 错误 75%、点 5-9 错误 100%）。

**根因**：workspace 放在 **x2 缓冲区内部**：

```cpp
ws = x2 + B*N*K*2 - 1024*4;   // 落在 x2 尾部 4KB
```

主 kernel 在**计算过程中**就往 `ws[u]` 写部分和，**而其它核此时还在读 x2**：

| 时刻 | 核 A（batch 少，先算完）| 核 B（batch 多，仍在计算）|
| :--- | :--- | :--- |
| t1 | 算完，写 `ws[u]` | 正在读 x2 |
| t2 | — | **读到已被 ws 覆盖的 x2 尾部** ❌ |

**这完美解释失败形态**：
- 点 1-3 全对 → 规模小，各核完成时间相近，来不及互相踩
- **点 4 错误 75% → 部分 batch 被踩坏、部分没被踩**
- 点 5-9 全错 → 规模大，时间差拉大，全部被踩
- 点 10 超时 → 额外开销

**同时解释了非确定性**——竞态的表现就是每次结果不同。

**重要结论**：**跨核聚合本身是通的**（否则点 4 应 100% 错误、点 1-3 也不可能
全对）。之前的判断"平台不支持跨核聚合"是**错的**。

### 11. 编译优化级别（-O2）

| 形状 | -O0（默认） | -O2 |
| :--- | --: | --: |
| 1×512×512×256 | 952 ms | 958 ms |
| 1×1024×1024×256 | 3584 ms | 3601 ms |

**无改善**（确认 `-O2` 已生效——flags 里有）。说明瓶颈不在编译器优化，
而在仿真每次操作的固定开销。

## 数学上不可行的方向

| 方向 | 为什么不可行 |
| :--- | :--- |
| 减少乘加次数 | `max_n dot(x1_m, x2_n)` 需算出所有点积 |
| 减少访存次数 | 每个 MAC 必须读两个操作数，读次数恒为 `2·M·N·K` |
| 提高算术强度 | x1 需 4MB、UB 仅 192KB，放不下；且每字节输入约对应 1 次乘加 |

## 唯一未穷尽的方向：提高并行度

**现状**：并行度上限为 `min(B, cores)`。**若某个测试点的 B 很小，多数核将空闲。**

**障碍**：按 (b, m 区间) 切分需要跨核归约，而：

- `AscendC::AtomicAdd` **仅支持 `__NPU_ARCH__` 5102/3510**，本项目是 2201 → 不可用
- `CrossCoreSetFlag`/`WaitFlag` 在 CPU 仿真下**行为不一致** → 无法本地验证
- 平台只调用一次 `run_kernel` → 无法用第二个 kernel 做最终归约

**该方向只能盲提交，且收益取决于平台实际核数与 B。**

## 结论

**标量路径的本地可验证优化已穷尽。** 上表 7 类尝试覆盖了：
分支、展开、批量搬运、裸指针、边界检查、循环重排、算法剪枝。

若要继续，只剩"提高并行度"（需盲提交）或"真机验证向量收益"两条路。
