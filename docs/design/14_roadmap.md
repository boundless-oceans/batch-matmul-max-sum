## 三、可优化的方法（按"本地能否验证"分类）

### A 类：本地能可靠验证 —— 推荐优先

判据：**减少"操作总数"**（访存次数、指令数）。与仿真实现无关。

| # | 方法 | 原理 | 预期 | 状态 |
| :-: | :--- | :--- | :--- | :--- |
| A1 | **按列复用 x2** | 同一列 x2 被 M 行复用，避免重读 | 减少 GM 读 M 倍 | ✅ **已实施**（9.9s→7.7s） |
| A2 | **按行分块复用 x1** | 把 x1 的 (M_block, K) 块载入 UB 后复用 | 减少 x1 的 GM 读 | 待评估 |
| A3 | 压低标量准备开销 | 减少 `SetValue`/`GetValue` 调用次数 | 直接减少指令数 | 待评估 |
| A4 | 提高并行度 | 按 (b, m 区间) 切分；平台核数未知 | 上限 `min(B, cores)` | ⚠️ 需跨核归约 |

**关于 A2 的权衡（重要）**：本问题是**访存受限**——总读取次数恒为
`2·M·N·K`（每个 MAC 需两个操作数）。分块只能改变"读自 GM 还是 UB"，
**不能减少读取总次数**：

```
不分块:  x1 读 M·N·K 次（全从 GM）+ x2 读 M·N·K 次（全从 UB）
分块:    两者都读 M·N·K 次，但 x1 的 (M·N·K / M_block) 次来自 GM
```

**而实测表明 UB 读与 GM 读在仿真下成本相近**（2031ms vs 2047ms），
故 A2 **本地测不出收益**；真机上若 UB 显著快于 GM 才有收益。

### B 类：本地只能验正确性、测不出收益

| # | 方法 | 为什么本地测不出 |
| :-: | :--- | :--- |
| B1 | **向量化** | 仿真的向量运算按元素访存，每元素约 5.5 ns，与标量（7.1 ns）接近。**收益来自真机向量单元的每元素成本优势**，仿真无法体现 |
| B2 | **Cube（`Mmad`）** | 高层 `Matmul` 在仿真下挂住；底层需自拼 `GM→L1→L0A/B→Mmad→L0C→GM` 数据流 |
| B3 | 跨核协同 | CPU 仿真下跨核 flag 行为不一致 |

**B1/B2 若要成功，前提是先把"喂数据的成本"压到标量版之下**
（向量化失败两次，正是败在这里：标量准备开销是标量版的 8 倍）。

### C 类：已排除（附依据）

| # | 方法 | 排除依据 |
| :-: | :--- | :--- |
| C1 | 裸指针绕开 `GetValue` | 平台 Runtime Error——**收益来自仿真特性，真机不成立** |
| C2 | 上界剪枝（Cauchy-Schwarz） | 实测加速比 **1.00x**（标准正态数据下上界过松） |
| C3 | 装 ops 包 | 仿真库未定义任何指向 ops 的符号 |
| C4 | 提高算术强度（数据复用） | 数学上不可行：每个 MAC 必须读两个操作数，UB 放不下整个 x1（4MB vs 192KB） |
| C5 | 减少计算量 | 数学上不可行：`max_n dot(x1_m, x2_n)` 需算出所有点积 |

## 四、核心矛盾（必须正视）

| 事实 | 含义 |
| :--- | :--- |
| 本问题是**访存受限**，非算力受限 | 每字节输入约对应 1 次乘加，算术密度极低 |
| 仿真的向量每元素成本（5.5 ns）与标量（7.1 ns）接近 | 因为仿真同样按元素访存 |
| 唯一能大幅降低"每元素成本"的是**真机的向量/Cube 单元** | 而这**本地完全测不出** |

**故**：标量微优化已接近极限（A 类剩余空间有限）；
要达标大概率必须用向量/Cube，且**只能靠真机验证收益**。

## 六、若走向量化，正确的做法（吸取两次失败教训）

**两次失败的原因相同**：为每个 `(rows, 64)` tile 逐元素 `SetValue`，
标量操作数达标量版的 **8.1 倍**。

**正确的设计必须满足**：

1. 用 `DataCopy`（批量搬运）而非逐元素 `SetValue` 准备数据
2. 归约用 `WholeReduceSum`（一次 repeat 归约整行 64 个 fp32）
3. **估算公式**：`标量准备操作数 < 标量版的 M·N·K`——否则不可能更快
4. 优先让**向量指令数**而非**tile 数**最小化
