# 诊断：平凡 kernel（分离环境问题与计算问题）

## 为什么要做这个诊断

### 触发它的关键发现

从平台各测试点的**最优用时**反推运算量（假设最优实现约 1 MAC/cycle @1.8GHz）：

| 项 | 推算 MACs |
| :--- | --: |
| 平台 15 个测试点**合计** | 约 **60 万** |
| 其中测试点 8（超时那个） | 约 **3.1 万** |

而**本地构造的 `large_square`（B=4,M=N=1024,K=256）是 10.7 亿 MACs——
比平台全部测试点合计还大 1790 倍**。

### 更要紧的一条：本地耗时不能用

**本地 driver 会在 CPU 上做 O(B*M*N*K) 的 FP64 参考计算**，所以"进程总耗时"
主要花在验证上，而非 kernel。实测：把 kernel 换成**只写常量**的平凡核，
`4 1024 1024 256` 仍需 3830ms —— 那全是参考计算的耗时。

平台只跑 kernel（参考值是预先算好的），故**本地秒数对平台的超时判断无参考价值**。

### 由此得到的矛盾

```
测试点 8 约 3.1 万 MACs
本地实测该规模的纯计算 ≈ 0.5 ms
平台超时 = 3000 ms
=> 相差约 6000 倍
```

**即使 MAC 估算错 100 倍，也只需约 50ms。故超时几乎不可能由计算量造成。**

## 诊断设计

把 kernel 换成**平凡核**：不读 x1/x2、不做任何乘加、不依赖任何形状，
只把 `y` 的每个元素写成一个常量。

保留与正式实现**完全相同**的调用路径（`run_kernel` 签名、`usedCores`
计算、`<<<>>>` / `ICPU_RUN_KF` 双分支），故**唯一的变量是"是否做计算"**。

## 结果判读

| 平台结果 | 含义 | 下一步 |
| :--- | :--- | :--- |
| 平凡核**仍超时** | 问题与计算无关——出在环境/接口/调用路径层面 | 查核数、workspace、同步、超时判据 |
| 平凡核**通过（但 Wrong Answer）** | 计算路径本身能跑通 | 问题在原实现的计算里，需定位是哪个形状触发挂起 |
| 平凡核**Runtime Error** | 连最简路径都跑不通 | 查接口用法（如 dtype 分派、指针传递） |

**注意**：平凡核写的是常量，**必然 Wrong Answer**——这是预期行为，
不是失败。本次提交**只看"是否超时"与"是否崩溃"**。

## 这一版与正式版的差异

- 新增 `diag_trivial_kernel`（只写常量）
- `run_kernel` 改为启动平凡核
- **未改动**：签名、dtype 解析、`ResolveDims`、`usedCores` 计算、启动方式

正式实现（`batch_matmul_max_sum_custom`）**仍保留在文件中**，诊断后恢复即可。
