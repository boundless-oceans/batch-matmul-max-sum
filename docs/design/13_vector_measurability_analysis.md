# 澄清：本地仿真到底能不能测向量性能

**结论：能测，但测不出向量的优势——因为这个问题的瓶颈是访存，不是算力。**

## 一、先更正一个错误结论

此前记录"仿真把向量指令逐元素模拟，64 元素一次约 1.5 ms"，据此判定
"向量收益本地完全测不出"。**该结论错误**，错在把进程启动开销算进了
单次调用（1262ms 里大半是启动）。

**正确的测量**（固定 256 轮，只变 tile 大小）：

| tile 元素数 | 256 次 `Mul` 总耗时 | 每元素 |
| --: | --: | --: |
| 64 | 234 ms（启动主导） | — |
| 1024 | 1455 ms | **约 5.5 ns** |
| 16384 | 14595 ms | **约 3.5 ns** |

**即：仿真下向量运算"按元素处理、但速度接近原生"（3.5–5.5 ns/元素），
既不是"每次固定 1ms"，也不是"比标量慢 2000 倍"。**

## 二、那为什么向量版反而慢？

A/B 实测（同一 driver、同一形状、只测 kernel 时间）：

| 版本 | 1×256×256×256 | 1×512×512×256 |
| :--- | --: | --: |
| 标量版 | **319 ms** | **988 ms** |
| 向量版 | **> 60 s** | — |

原因**不是向量运算慢**，而是**标量准备开销**：

| | 标量操作数 |
| :--- | --: |
| 标量版 | `B*M*N*K` = 1.68e7 |
| 向量版（为 (4,64) tile 逐个 `SetValue`） | **1.35e8（8.1 倍）** |

**即使向量运算完全免费，向量版也更慢——因为喂数据的成本超过了对标量版的节省。**

## 三、更根本的原因：本问题是访存瓶颈

| 单元 | 每元素成本 |
| :--- | --: |
| 标量（仿真） | 约 7.1 ns |
| **向量（仿真）** | **约 5.5 ns** |

**两者接近。** 因为仿真的向量运算要按元素做访存（这个问题的瓶颈正是访存：
`M*N*K` 次乘法，每次至少 2 次操作数读取）。

**故在真机上：**

- 若向量单元 + 片上带宽能显著降低"每元素访问成本"，向量化才有大收益
- 若仍是片外带宽受限（x1 需 4MB、UB 仅 192KB，必须反复从 GM 读），
  **向量化收益有限**——因为瓶颈不在算力

这个问题的算术密度极低：**每字节输入只对应一次乘加**（K=256 时，
每个数据元素参与 256 次乘加，但每次都要重新读）。

## 四、对"是否上真机"的建议

| 问题 | 本地能否回答 |
| :--- | :--- |
| 正确性 | ✅ 完全可测 |
| 标量实现的耗时 | ✅ 可测（且与真机同源，都是逐条指令） |
| **向量化的耗时收益** | ⚠️ **只能测"操作数是否减少"**，测不出硬件的每元素成本优势 |
| **Cube 的收益** | ❌ 高层 `Matmul` 在仿真下挂住 |

**故真机的价值在于**：回答"向量/Cube 单元的每元素成本是否远低于标量"。
若远低，向量化有大收益；若接近，则本问题在真机上同样受限于访存，
**换实现语言也救不了**。

## 五、因此本地仍值得做的方向

1. **正确性**（已充分覆盖）
2. **减少操作总数**——这是本地**能可靠测量**的指标：
   - 减少 GM 读取次数（如"按列复用 x2"就是此类，已见效）
   - 减少标量准备开销
   - **不**依赖"向量指令更快"这个本地测不出的假设

按此标准，向量化若要成功，**必须先把标量准备开销压到标量版之下**，
否则在本问题和本仿真下都不划算。
